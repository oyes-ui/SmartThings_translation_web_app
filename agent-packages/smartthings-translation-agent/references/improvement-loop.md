# 업무 종료 후 최소 개선 루프

업무 종료 시에는 확정된 사실을 남기고, 사용자가 요청하면 그 기록에서 개선안 하나를 골라 검증한다.
별도 사용자 명령·전역 DB·상시 실행기는 추가하지 않는다. 산출물을 다듬는
[1차 개선 모드](workflow-guide.md#1차-개선-모드)와 달리, 이 문서는 다음 업무의 절차·판단을 개선하는 지침이다.

## 적용 범위와 현재 지원

이 문서는 활성 에이전트의 운영 지침이다. CLI 종료 hook이나 백그라운드 자동 분석을 구현한 것이 아니다.
여기서 **자동**은 사용자가 맡긴 업무의 단계 종료 시 에이전트가 별도 회고 요청 없이 수행한다는 뜻이다.
단순 Q&A·상태 조회 때는 종료 기록을 새로 만들거나 기존 작업을 실행하지 않는다.

현재 구현된 것은 표준 검수 `changes[]` manifest를 사용하는 납품 경로의 작업별
`outcome_ledger` 기록, `review_outcomes.py`의 기록·집계, `quality_scorecard.py`의 비교다.
일반 편집·번역·native `decisions` manifest 등 모든 경로가 outcome을 자동 생성하는 것은 아니다.
반복 패턴 추출·개선안 작성·변경 전후 비교는 요청 시 에이전트가 수행하며 전용 실행기는 없다.

## 자동으로 할 일과 요청할 때 할 일

| 구분 | 업무 종료 시 기본 수행 | 사용자 요청 시 수행 |
| --- | --- | --- |
| 범위 | 현재 대화에 연결된 작업과 기존 근거만 확인 | 지정한 작업·기간의 기록 비교 |
| 사람 판단 | 지원 경로의 승인·수정 승인·거절 기록 확인 | 여러 작업의 수용 경향·거절 이유 분석 |
| 실행 결과 | 검증 통과·실패·미완료와 산출물 경로 확인 | 실패·재작업의 원인 가설과 반복 여부 분석 |
| 개선 신호 | 작은 번역·진행 오류와 사용자 지적도 근거·조치와 함께 짧게 기록 | 재사용 가능한 개선안과 적용 범위 제안 |
| 변경 | 현 업무의 기존 승인 범위만 실행 | 요청·승인한 개선안을 규칙·절차·도구의 해당 정본에 반영 |
| 효과 확인 | 수행하지 않은 평가를 완료로 표시하지 않음 | 변경 전후 검증과 이후 해당 업무에서의 효과 확인 |

회고 요청은 분석 범위다. 변경 요청·기존 승인이 반영까지 포함하면 같은 승인을 다시 묻지 않는다.
업무 문안의 승인을 전역 규칙·용어집·RAG 변경 승인으로 확대하지 않는다. 유료 평가·재시도와
외부 저장은 각각 기존 비용·도구 승인 규칙을 따른다.

## 업무 종료 시 기본 절차

1. **단계의 실제 상태를 확인한다.** 검수 제안 완료·사용자 판단 대기·draft 생성·납품 완료·실패를
   구분한다. 납품 완료 기준은 [실행 규약](command-execution.md)을 따른다.
2. **확정 판단과 실행 결과를 연결한다.** 반환된 `outcome_ledger`가 있으면 현재 작업의
   ledger와 원본 승인 manifest를 확인한다. 승인·수정 승인·거절 수와 미결정 수는 기존 근거에서만
   산출한다. `proposed_after`를 보존하고 미결정을 거절로 만들지 않는다.
3. **지원하지 않는 기록은 만들지 않는다.** 호환 manifest나 사람 판정이 없으면
   `outcome 기록 대상 없음` 또는 `사람 판단 대기`로 안내한다. 직접 지정한 편집이나 실패를
   가상의 에이전트 제안·거절로 변환하지 않는다. 실행 실패는 기존 journal·리포트에 남긴다.
4. **현재 업무 결과에 짧게 붙이고 종료한다.** 상태·판단 요약·기록 경로를 기존 완료 답변이나
   기존 작업 리포트에 포함한다. 이미 확인한 교정·실패가 있을 때만 개선 신호를 덧붙인다.
   추가 근거가 없으면 교훈이나 개선안을 억지로 만들지 않는다.

예시(실제 확인한 수치로만 작성):

> 납품 검증 완료. 제안 그대로 승인 8건·수정 후 승인 1건·거절 1건·미결정 2건.
> 확정 판단 10건은 작업별 outcome에 기록됨: {반환된 경로}.
> 거절 이유로 제목 괄호 예외 누락이 확인됨. 반복 여부·개선안은 미분석.

새 회고 파일·누적 ledger·평가 세트를 자동 생성하지 않고 전체 이력을 탐색하지 않는다.
기록이 실패하면 `기록 실패`를 알리고 기존 실행 결과의 검증 상태와 구분한다. 기록을 복구하려고
번역·납품 전체를 재실행하지 않는다. 이미 발행된 contract·result·배치·워크북도 사후 수정하지 않는다.
완료 결과를 재조회·재개한 것은 새 작업 사례로 세지 않는다.
개선안이나 효과 평가가 없다는 이유로 검증된 업무 산출물의 완료를 보류하지 않는다.

## 업무 중 작은 오류·지적도 개선 근거로 남기기

심각도와 무관하게 실제 확인된 교정은 대상이다. 예를 들면 다음과 같다.

| 종류 | 예시 | 우선 처리 |
| --- | --- | --- |
| 번역·표현 | 오탈자·띄어쓰기·대소문자·어미·괄호, 사용자 문체 지적 | 해당 문구·언어·section의 적용 범위 확인 |
| 도구·산출물 | 잘못된 인자·파일 경로·셀 주소, 끊긴 링크·보고 수치 오류 | 도움말·현재 파일·실제 결과와 대조 |
| 업무 진행 | 이미 준 정보 재질문, 중복 승인 요청, 단계 누락·잘못된 완료 안내 | 기존 대화·승인·단계 상태와 대조 |

**현재 작업의 교정은 즉시 처리하고, 재사용할 변경은 구분한다.** 사용자의 지적을 받거나
에이전트가 오류를 직접 확인하면 해당 범위를 확인해 현재 승인 안에서 바로 고친다.
Excel은 기존 승인·검증 저장 경로를 유지하고, 유료 재시도는 별도 비용 규칙을 따른다.
현재 작업의 교정을 이후 작업 전체에 대한 규칙 변경으로 확대하지 않는다.
사용자 선호·특정 story의 예외·확인된 오류·미확인 지적을 구분하며, 미확인 사항은 사실로 기록하지 않는다.

기록은 **지적/확인 근거 → 조치·확인 결과 → 적용 범위 → 재발 방지 후보** 한 줄이면 충분하다.
재발 방지 후보가 없으면 `이번 작업에서 종결`, 원인이 미확인이면 `원인 미확인`으로 남긴다.
같은 작업에서 같은 지적은 묶어 갱신하고 횟수를 부풀리지 않는다.

> 도구 오류: 지원하지 않는 CLI 옵션 사용(오류 출력 확인) → 도움말의 옵션으로 교정·성공 확인
> → 이 도구 호출에 한정 → 호출 전 옵션 확인 절차 후보, 미반영.

번역 제안에 대한 확정 판단이 기존 outcome에 있으면 그 항목을 참조하고 중복 기록하지 않는다.
그 밖의 오류·지적은 outcome의 승인/거절 통계에 섞지 않는다. 이미 작성·갱신 중인 workspace
작업 리포트에 보존 가능한 영역이 있으면 `작업 중 교정 메모`로 덧붙인다. 자동 생성 블록과
사용자 메모는 덮어쓰지 않으며, 쓰기 권한·관리 범위가 불명확한 문서는 수정하지 않는다.
그런 리포트가 없으면 기존 완료 답변에만 요약한다. 별도 저장소나 회고 파일을 자동 생성하지 않는다.
대화에만 남긴 메모의 다음 대화 재사용은 보장하지 않으며, 지속 보관을 요청하면 지정한 작업
리포트에 저장하고 이후 분석에서 그 경로를 참조한다. vault·외부 서비스는 기존 저장 권한을 따른다.

작은 지적 한 건도 요청 시 개선 후보가 될 수 있으며 반복 발생을 필수 조건으로 삼지 않는다.
다만 한 번의 오탈자나 문체 선호만으로 공통 규칙을 만들지 않는다. 재발 가능성·다른 작업의 적용성·
변경 비용을 보고 `이번 작업에서 종결` 또는 `재사용할 개선 후보`를 구분한다.
후보의 원인 분석·공통 절차/도구 변경·효과 확인은 아래의 요청 기반 절차로 연결한다.

## 요청 시 최소 개선 절차

“이번 작업에서 개선할 점 찾아줘”, “최근 승인 결과로 반복 문제를 봐줘”를 `/st-ask` 또는
자연어로 받는다. 현재 대화의 대상·범위를 재사용하고 여러 작업 중 대상이 모호할 때만 확인한다.

1. **근거를 모은다.** 지정 작업의 ledger, 원본 승인 manifest, 실행 결과·journal을 연결한다.
   언어·원문 그룹·section 역할·용어집/규칙/도구 버전은 기존 packet·contract에서 확인한다.
   없는 정보는 미확인으로 두며 동일 조건이라고 가정하지 않는다.
2. **후보를 선별한다.** 반복되는 오류·불필요한 수정·재작업, 작은 번역·진행 오류와 사용자 교정,
   단건의 중대한 실패 중 근거가 충분하고 재사용할 가치가 있는 것을 고른다. 같은 작업의 재개나 같은 문자열 복제는 독립 반복으로 세지 않는다.
   수정 승인·거절만으로 오류를 단정하지 않고 의미/규칙 문제와 문체 선호를 구분한다.
3. **작은 개선안 하나를 제안한다.** 먼저 기존 규칙의 존재와 실제 전달 여부를 확인한다.
   규칙을 못 읽었으면 로딩·체크리스트, 정본 자체가 틀렸으면 해당 정본, 특정 story의 예외면
   그 적용 범위를 고친다. 임시 예외를 전역 규칙으로 올리지 않는다.
4. **요청·승인 범위에 맞춰 검증·반영한다.** 분석 요청이면 제안까지다. 변경까지 요청받았다면
   해당 정본과 필요한 검증을 수정한다. 패키지 지침은 이 패키지에, 번역 규칙·용어집은
   [규칙 출처](rules-sources.md)와 기존 관리 경로에 반영한다. 원복 방법도 남긴다.
5. **효과를 확인한다.** 과거 문제의 재현·정상 사례의 유지·가능하면 개선안 작성에 쓰지 않은
   사례를 비교한다. 다음 해당 업무에서 확인할 항목을 기존 개선 기록에 남긴다. 그 업무까지
   평가 범위가 승인되어 있고 기록이 연결된 경우에만 후속 확인한다. 미승인 가설은 판단 근거로 강제하지 않는다.

새 schema나 상태 머신 없이 대화 또는 요청받은 작업 리포트에 다음을 남긴다.

- **근거:** ledger의 항목 식별자, 원본 판단 이유, 관련 실행 기록.
- **원인 가설과 변경안:** 무엇이 빠졌는지, 어느 정본을 어떻게 바꿀지.
- **적용 범위:** 언어·section·story 조건, 일반 규칙 또는 한정 예외.
- **검증:** 변경 전후 결과, 정상 유지 사례, 평가하지 못한 범위.
- **후속 확인·원복:** 다음 해당 업무에서 볼 항목, 되돌릴 위치·버전.

결론은 `개선 불필요`, `근거 부족으로 보류`, `변경 제안`, `반영 후 효과 확인 대기`,
`효과 확인 완료`처럼 실제 진행에 맞춰 쓴다. 별도 기계 상태를 추가하는 것은 아니다.
후보가 없거나 근거가 부족하면 종료한다. 해결되거나 보류한 동일 근거를 매번 재분석하지 않는다.

## 기존 기록·측정 도구 사용 시 주의

- outcome은 **사람의 판단**이고 실행 성공 증명이 아니다. 실제 반영 여부는 독립 검증 결과와 연결한다.
- 작업별 ledger를 정본으로 재사용한다. 식별에는 작업 경로/`work_id`와 `(report_id, finding_id)`를
  함께 확인한다. 누적 ledger는 사용자가 요청한 경우에만 기존 `append_ledger`를 사용하며,
  이 함수의 중복 제거 키는 `(report_id, finding_id)`다. ID가 비거나 작업 간 충돌하면 원본을
  수정하지 말고 작업별로 분리해 분석한다.
- `review_outcomes.py --ledger <기존 ledger>`는 읽기·집계다. `--manifest`는 기록을 변경하므로
  호환되는 승인/거절 완료 행만 준다. pending이 섞인 원본 전체를 넘기면 거부된다.
- `scorecard_inputs`와 scorecard는 `finding_id`만 평가 ID로 사용한다. 여러 작업을 합친 데이터의
  ID 유일성을 확인하지 않은 채 점수를 내지 않는다. 최소 운영에서는 작업별로 평가한다.
- ledger의 제안 수용률은 **검토된 제안**의 수치다. 제안하지 않은 셀의 오류·유지 적합성은
  포함되지 않으므로 전체 정확도나 누락률로 표현하지 않는다.
  기록이 0건이면 평가 자료 없음으로 보고한다. 최초 `proposed_after`가 남지 않은 기록은
  그대로 승인과 수정 승인을 신뢰성 있게 구분할 수 없으므로 그 한계를 밝힌다.
- 전체 품질 검증에는 사람이 독립적으로 확인한 누락 오류와 정상 유지 셀도 포함한다.
  이들은 ledger에 가짜 제안으로 넣지 않고 요청 시 만드는 별도 평가 세트에서 비교한다.
- `independence: suspect`는 기본 점수에서 제외한다. 일반 요약은 suspect도 포함하므로
  분모와 제외 수를 밝힌다. `verified` 표시는 이 코드의 anchoring 경고 여부이지 외부 정답 인증이 아니다.
- 문자열 exact match는 문안 일치 지표다. 허용 가능한 번역 변형은 별도 판단한다.
  `critical_missed_changes: 0`이나 `shadow_exit_ready: true`만으로 품질 통과·자동 승인·승인 완화를 결정하지 않는다.

## 설계 확인 시나리오

| 상황 | 기대 동작 |
| --- | --- |
| 검수 제안만 완료, 사람 판단 없음 | 판단 대기로 종료; outcome·수용률을 만들지 않음 |
| 승인·거절·pending이 섞인 표준 납품 | 확정 행의 기존 ledger와 실제 납품 검증 확인; pending은 별도 보고 |
| 직접 지정한 draft 편집 완료 | draft·검증 결과 안내; 호환 기록이 없으면 outcome 대상 없음 |
| 기록 실패 또는 납품 검증 실패 | 각각 사실대로 구분 보고; 가짜 거절·완료를 만들지 않음 |
| 같은 작업 재개·상태 조회 | 기존 결과 재사용; 새 사례·회고 실행을 만들지 않음 |
| 작은 번역 지적 또는 옵션·링크·중복 질문 오류 | 현재 승인 범위에서 교정·확인하고 기존 리포트/완료 답변에 짧게 기록 |
| 취향·한정 예외 또는 미확인 지적 | 적용 범위·확인 여부 표시; 전역 규칙이나 오류 통계로 승격하지 않음 |
| 작은 지적 한 건의 재발 방지 요청 | 반복 횟수와 무관하게 원인·적용성 검토; 가치가 있으면 작은 개선안 제안 |
| 회고만 요청 | 근거와 개선안까지; 규칙·용어집·코드 변경 없음 |
| 개선안 반영까지 요청 | 기존 승인 재사용, 범위 내 변경·검증; 실제 효과 미확인 시 대기로 기록 |
| 다음 업무에서 연결된 개선 확인 | 승인된 범위에서 재발·정상 유지 확인; 과거 산출물 재생성 없음 |
